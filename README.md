# Bluepax Flow: A git flow of bluepax&reg;
----------
此flow通过git flow更改而来，适用于bluepax&reg;团队，第三个版本

第三版相对第二版的变化：预发布版本号改为 `X.0.0-beta.N`；X.0.0 即正式版，只有 X.0.0 有 beta；新增版本代号规则；提交类型与 Conventional Commits 工具链对齐；热修复也走合并请求；权限角色对应到 GitHub；提交信息与标签注释统一使用英文。



## 0. 版本规定
版本号管理采用[SemVer2.0](https://semver.org/lang/zh-CN/)，版本号最低从 `1.0.0-beta.1` 开始，并规范使用 beta 作为唯一预发布阶段标识。

- 预发布只用于新主版本：`X.0.0-beta.N`，N 为该版本对应的 build 号；之后发布的 `X.0.0` 即正式版。次版本与修订版（如 `X.1.0`、`X.0.1`）不设 beta，直接发布正式版。
- build 号从 1 开始，一个 **dev** 提交对应一个 build 号（`git rev-list --count --first-parent <dev提交>`）：每次合入 **dev** 的合并提交计一个 build，功能分支内部的提交不计入；顺序递增，每一个发布版本都有对应唯一的 build 号。
- 所有版本要求在 about 界面标明版本号、build 号、编译时间与提交号。
- 版本代号取天空中的生物，用一个英文小写单词（如 `swift`、`kestrel`、`albatross`）。同一主版本 X 的全部版本（含发布前的 beta）共用一个代号，新主版本换新代号，代号不重复使用。
- 不使用 `+build.N` 构建元数据：SemVer 比较会忽略 `+` 之后的内容，Docker 镜像标签也不允许 `+`。

一个标准的预发行版本的例子：`4.0.0-beta.3286`；正式发行版本的例子：`4.0.0`、`4.0.1`、`4.1.0`。

## 1. 分支结构

- **main** ：分支主要用于版本释放，不允许直接对其进行代码修改和提交，所有的提交都必须有对应的版本tag和tag注释，第一个版本和tag内容至少为 `v1.0.0-beta.1`，tag注释内容为版本代号和英文说明，如："swift; take off light and fast"

- **dev** ：主要开发和热修复分支，也是仓库默认分支。并在此初始化项目，其中第一次提交时使用此唯一的提交信息：`init: init the project and add basic files`。强调合并进 **dev** 分支的内容必须保证完整性，能随时合并进main分支进行发布。热修复也合入此分支，即使其包含未发布的内容。以此方式倒逼 **dev** 分支的强健性和软件的体验感。此分支上一个提交对应一个修复或更新。

- **feature/xxxx**、**fix/xxxx**：父分支为 **dev** 。主要功能和代码更新以及对应部分的bug修复的分支。分支命名方式以主要开发功能为主。当 **dev** 分支有提交更新时，必须合并一次到此分支进行融合性测试，合并入 **dev** 前必须已包含 **dev** 的最新提交并通过 CI。



## 2. 细节
##### 权限控制
- 以下基本权限由低到高依次往下排列：
[成员]（GitHub：Contributor）只能在所负责的分支或自己的 fork 上进行提交操作并提交合并请求（PR）。
[组长]（GitHub：Maintainer，由 `CODEOWNERS` 指定负责范围）审核所负责模块的合并请求，维护其负责部分的完整性。
[项目主管部]（GitHub：仓库所有者，即组织 Owner 账号）管理 **dev** 分支，审核合并请求、处理热修复，并负责对 **main** 分支进行操作，将 **dev** 分支合入完成版本迭代。
- 单人维护时由所有者账号承担全部角色。GitHub 不允许批准自己的合并请求，此时 **dev** 的必需批准数设为 0，有其他协作者后改为 1。

##### 提交
- 所有提交信息（含 **main** 的版本提交与合并提交）一律使用英文，描述以动词原形开头，首字母小写，不加句号；版本提交的正文每行首字母大写。标签注释同样使用英文。
- 提交的信息规范参考 [Conventional Commits](https://www.conventionalcommits.org/zh-hans/)，并有修改，一般提交信息的具体规范：
```commit
<类型>[(范围)][!]: <描述>
<BLANK LINE>
[可选的正文]

||||||||||||||||||||||||||||||||||||||||||||||||||||||||||||
<类型>：
  feat: 新功能、新特性
  fix: bug修复完成
  perf: 更改代码，性能优化
  refactor: 代码重构(在不影响代码内部行为、功能下的代码修改)
  docs: 文档资源改动
  test: 测试代码部分的改动
  build: 项目结构、依赖与构建配置的改动(原 structure)
  ci: 持续集成配置的改动
  revert: 恢复上一次提交
  chore: 不属于以上类型，但必须要描述清楚改动(原 null)
  init: 仅用于第一次提交

<范围>：
  可选，模块或包名，例如 feat(storage): ...

<!>：
  破坏性变更，升主版本号；也可在正文写 BREAKING CHANGE:

<描述>：
  加上issue编号后缀，例如#9999，如果有的话。

<BLANK LINE>：
  空行

[可选的正文]：
  补充说明，不常用。
```

- 对于 **main** 分支进行版本迭代时，其提交信息的规范按照如下特别规定：
```commit
<版本代号>(vX.Y.Z | vX.0.0-beta.N): <新版本简述>
<BLANK LINE>
<必须的正文>

||||||||||||||||||||||||||||||||||||||||||||||||||||||||||||
第一行例子：
  swift(v1.0.0-beta.512): open the public beta

<BLANK LINE>：
  空行

<必须的正文>：
  使用英文，每行首字母大写，无句号，大概格式以类似如下进行，主要为与上一次版本的差异更新集合（可用 git-cliff 生成）：
    <feature>
    Improve the performance of ** #7843
    Add ** #45621
    <bug>
    Fix .... #121
    Fix .... #892
```

##### 合并
- 合并一律保留完整提交历史，禁止 squash 与 rebase 合并。功能分支、修复分支与热修复合入 **dev** 使用合并提交（GitHub 的 Create a merge commit，等同 `--no-ff`），合并请求中的每个提交都须符合提交规范；合并提交保留默认信息，生成变更列表时跳过。
- [项目主管部] 将 **dev** 合入 **main** 时必须使用以下参数，完整示范：`git merge --no-ff --no-commit dev`。即要求merge后检查代码无误后再手动commit，并打附注标签 `git tag -a vX.Y.Z -m "<代号>; <英文说明>"`。


## 3. 注意
- 对分支破坏性的操作是不被允许的（main 与 dev 开启分支保护：禁止 force push、禁止删除、禁止改写历史）
- 在push前必须pull，只对自己负责的部分进行push和合并请求
- 禁止reset，不对共享分支 rebase
